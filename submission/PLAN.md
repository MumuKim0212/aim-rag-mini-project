# RAG 실험 계획

작성일: 2026-10-20

## 1. 목적과 가설

**목적**: 금융 PDF 23개를 검색해 파일명·페이지 근거와 함께 한국어로 답하는 RAG Agent를 만든다. 문서로 답할 수 없는 질문에는 확인·정정·보류·거절로 대응하게 한다. 품질과 비용(USD·토큰·시간)을 함께 측정해 가장 싼 설정 중 충분히 좋은 것을 고른다.

**가설** (각각 실험 카드로 검증)

| # | 가설 | 근거 |
|---|---|---|
| H1 | 문서 구조 단위 청킹(용어집은 용어 단위, 약관은 조항 단위, 가이드는 제목 단위)이 Recursive보다 근거 페이지를 더 온전하게 가져온다 | 용어집은 "용어 다음 줄에 정의", 약관은 `제N조(제목)` 구조라서 고정 길이로 자르면 정의·조항이 잘린다 |
| H2 | 청크에 문서명·조 제목을 붙이면 비슷한 조항이 여러 약관에 있을 때 검색이 정확해진다 | 15개 약관에 "약관의 적용", "통지" 같은 같은 이름의 조항이 반복된다 |
| H3 | 정확한 용어를 묻는 질문은 BM25가, 상황을 풀어 쓴 질문은 벡터 검색이 잘 맞고, Hybrid가 둘 다 무난하다 | 기본 세트는 용어 질문, 추가 세트는 "집은 있는데 생활비가…" 같은 상황 서술형이 많다 |
| H4 | Agent(질문 분류, 근거 판단, 재검색)는 negative 대응과 다중 근거 질문에서 기본 RAG보다 낫지만 비용이 2배 이상 든다 | negative 40문항에 기대 행동이 22종이다. 기본 RAG의 단일 프롬프트로는 되묻기·정정·거절을 구분하기 어렵다 |
| H5 | 최저가 답변 모델은 기초 문항에서 flash 등급과 차이가 작고, 고급·negative 문항에서 차이가 난다 | 기본 positive와 추가 세트에 고급 문항이 50개 있다 |

## 2. 사용할 PDF와 질문 세트

### 2.1 검색 범위 (인덱스)

| 범위 | 포함 PDF | 페이지 | 평가하는 세트 |
|---|---|---|---|
| A (기본) | 용어집 1개 + 표준약관 15개 | 142 (용어집 20쪽 이후 출처 목록은 제외) | 기본 positive POS001–060, 기본 negative NEG001–040 |
| B (전체) | A + 금융생활 가이드 + 추가 6개 | 490 | 금융생활 POS061–080, 추가 ADD-* 60문항, 직접 만든 골든셋 |

기본 negative의 "자료에 없음"은 범위 A 조건이므로 기본 세트는 반드시 범위 A로 평가한다.

### 2.2 질문 세트와 분할

| 세트 | 문항 | dev | test | 정답 근거 ID → (파일, 페이지) 변환 |
|---|---|---|---|---|
| 기본 positive | 60 | 30 | 30 | `fsc-glossary-N`: 용어집 출처 목록의 `dicId=N` → 용어 → 그 용어가 나오는 페이지. `kofia-terms-X-V-A`: 약관 1쪽의 `버전: V` → 파일, `A` → 제A조(추정, 1단계에서 검증) → 그 조항이 나오는 페이지 |
| 기본 negative | 40 | 20 | 20 | 8문항만 근거 ID가 있다(정정형). 나머지는 답변 불가 |
| 금융생활 positive | 20 | 10 | 10 | `fss-life-guide-pdf-N` = PDF N쪽 |
| 추가 positive | 60 | 30 | 30 | `<파일>-pdf-N` = PDF N쪽 |
| 직접 만든 골든셋 | 40 내외 | – | 전부 | 직접 기록 |

- 분할은 세트 × 난이도로 층화한다. negative는 유형(`category`)도 층화에 넣는다. 추가 세트는 문서별로 5:5로 나눈다.
- 분할 결과는 `golden/`에 고정 파일로 저장하고 시드를 기록한다. test는 8단계 전까지 열어 보지 않는다(LLM 없는 지표 포함).
- 제공 답안에는 원문 그대로의 근거 구절이 없다(`must_include`는 요약이다). 1단계에서 정답 페이지 원문에서 근거 구절을 뽑아 `evidence`에 넣고, 원문과 자동 대조해 검수한다.

### 2.3 직접 만든 골든셋 (README 요구사항)

| 유형 | 목표 문항 | 예 |
|---|---|---|
| 용어 정의 | 8 | 용어집·약관 정의 조항 |
| 조건 비교 | 8 | 두 약관의 같은 조항 비교, 가입 조건 A/B 비교 |
| 표·그래프 해석 | 8 | 가이드북·주택연금 표의 수치, 단위·각주 포함 |
| 다중 근거 | 6 | 두 문서 또는 두 페이지가 필요한 질문 |
| 답변 불가 | 10 | 주제는 다루지만 묻는 사실은 없는 근접 질문, 최신 정보, 개인 정보. `note`에 이유와 기대 대응(보류·확인·거절)을 적는다 |

- 형식과 검수 기준은 `golden/README.md`를 따른다. 질문은 문서 문구를 그대로 쓰지 말고 실제 사용자처럼 짧고 모호하게도 쓴다.
- 질문·기준 답안·골든셋 파일은 검색 인덱스에 넣지 않는다.

- 001–006의 답변 실행은 개선 여지 확인(`evalkit/headroom.py`)에서 upside − risk가 잡음보다 클 때만 한다. 통과하지 못한 실험은 LLM 없는 검색 지표로 비교 결과를 내고, 답변 실행을 생략한 이유를 카드에 남긴다(2026-10-20 결정).
- 007과 008은 바꾸는 것이 검색이 아니라 답변 단계라서 LLM 없는 대리 지표가 없다. 그래서 개선 여지를 미리 계산할 수 없고, 답변 실행 자체가 비교다. 008은 README 필수 비교다. 007은 기준 실행을 재사용하므로 `gemini-3.1-flash-lite`와 `gemini-3.8-flash` 2개만 새로 실행한다.
- 001–006에서 채택된 값은 다음 카드의 기준 설정이 된다. 바뀐 기준은 카드와 PROCESS.md에 기록한다.
- 007은 채택된 검색 설정 위에서, 008은 007에서 고른 답변 모델로 한다. Agent는 여러 요소가 함께 바뀌므로 결과를 전체 구성의 효과로 해석한다. 특정 노드의 효과를 주장하려면 그 노드만 끄는 실험을 따로 한다.
- 고정 조건: 질문 세트와 분할, 검색 범위(A/B), 채점 모델과 채점 프롬프트, 평가 방법.
- 최종 test는 세 시스템을 한 번씩 돌린다(2026-10-20 결정, `docs/WORKFLOW.md` 8단계): T1 처음 RAG, T2 개선된 RAG(채택된 설정 체인의 마지막), T3 Agent(T2와 같은 검색·답변 모델·프롬프트). 설정 튜닝의 효과 = T2 − T1, 구조의 효과 = T3 − T2. 세 설정 파일은 test 실행 전에 PROCESS.md 9절에 적고 커밋한다.

### 3.3 기본 RAG 프롬프트를 Agent와 같게 두는 이유

기본 RAG가 "근거가 없으면 보류"만 하는 최소 프롬프트를 쓰면, negative 문항(정정·되묻기·거절·주입)에서 Agent가 이기는 것이 당연해진다. 그 차이는 그래프 구조가 아니라 프롬프트에 적힌 규칙에서 나온다. 그래서 두 시스템이 같은 답변 프롬프트(`prompts/answer_v1.md`)를 쓴다. 008의 차이는 Agent가 더한 구조(질문 분류, 근거 충분성 판단, 재검색, 인용 검증)의 효과로 해석한다.

- 대가: Agent의 이득이 작게 나올 수 있다. 대신 나온 이득은 구조 덕분이라고 말할 수 있다.
- 기본 RAG는 LLM 1회로 status까지 고른다. Agent는 같은 판단을 classify·grade 노드로 나눠 여러 번 한다. 이 차이가 008에서 비교하는 대상이다.

## 4. 모델과 단가

### 4.1 후보 모델 (텍스트 답변·채점용)

유료 Standard 단가, USD / 1M 토큰. 출력 단가에는 thinking 토큰이 포함된다. 안정(stable) 모델만 쓴다: preview 모델과 Gemini 2.5 계열(신규 사용자 제한 접근)은 쓰지 않는다(2026-10-20 결정).

| 모델 ID | 등급 | 입력 | 출력 | 비고 |
|---|---|---|---|---|
| `gemini-3.1-flash-lite` | lite | 0.25 | 1.50 | 가장 싼 안정 모델 |
| `gemini-3.5-flash-lite` | lite | 0.30 | 2.50 | 공식 문서가 새 프로젝트에 권장 |
| `gemini-3.6-flash` | flash (이전 세대) | 0.75 | 3.75 | 2027-01-01부터 1.50 / 7.50 |
| `gemini-3.8-flash` | flash (최신) | 0.75 | 3.75 | 2027-01-01부터 1.50 / 7.50 |

- 제외: `gemini-4-argon`(안정, 입력 2.00 / 출력 10.00, 2026-12-01부터 2배). 이 실험 규모에는 과하다.
- Batch API는 단가가 절반이지만 응답 시간을 잴 수 없다. 응답 시간이 필요 없는 채점에만 고려한다.

### 4.2 임베딩 모델

| 모델 ID | 상태 | 입력 (텍스트) | 최대 입력 | 비고 |
|---|---|---|---|---|

### 4.3 역할 배정 (2026-10-20 확정)

기준 설정의 답변 모델은 출발점이다. 최종 답변 모델은 카드 007(`gemini-3.1-flash-lite`, `gemini-3.8-flash`와 비교) 결과로 정하고, 채택되면 이후 설정 체인의 `answer.model`이 바뀐다. 채점·임베딩 기준은 프로젝트 내내 고정한다(임베딩은 카드 006에서만 비교).

| 용도 | 모델 ID | 이유 |
|---|---|---|
| 답변 후보 1 (lite) | `gemini-3.1-flash-lite` | 가장 싼 안정 모델 |
| 답변 후보 2 (lite) — 기준 설정 | `gemini-3.5-flash-lite` | 공식 문서가 새 프로젝트에 권장하는 lite. 비용을 낮게 유지하면서 출발한다. temperature를 무시하므로(고정 샘플링) 3단계 (a) 재실행 잡음을 반드시 측정한다 |
| 답변 후보 3 (flash) | `gemini-3.8-flash` | 최신 flash. `gemini-3.6-flash`와 단가가 같다. 품질 상한을 확인하는 비교 대상 |
| 채점 (고정) | `gemini-3.6-flash` | 답변 후보와 다른 모델이면서 Pro보다 단가가 약 1/3이다. 채점 신뢰도는 8단계에서 사람이 10건을 검수해 확인한다 |
| 임베딩 기준 | `gemini-embedding-2` | 입력 한도가 8,192 토큰으로 넉넉하다 |
| 임베딩 비교 (006) | `gemini-embedding-001` | 더 싸고, `task_type`(질문/문서 구분) 효과도 볼 수 있다 |

thinking 토큰은 출력으로 과금된다. 답변·채점 모두 `thinking_level`을 `config`에 기록하고, 응답의 thinking 토큰 수를 출력 토큰과 따로 `steps`에 남긴다.

**호출 확인 결과 (2026-10-20, 같은 짧은 질문 1회씩)**

| 모델 | `thinking_level=low`의 thinking 토큰 | `high` | temperature |
|---|---|---|---|
| `gemini-3.8-flash` | 0 | 573 | 적용됨 |
| `gemini-3.6-flash` | 391 | 549 | 무시됨 (고정 샘플링) |
| `gemini-3.5-flash-lite` | 0 | 577 | 무시됨 (고정 샘플링) |
| `gemini-3.1-flash-lite` | 159 | 460 | 적용됨 |

- 같은 `low`라도 모델마다 thinking 양이 다르다. 007에서는 thinking 토큰을 따로 보고하고, 품질 차이를 모델 차이와 thinking 차이로 나눠 해석하지 않는다(둘이 함께 바뀐다).
- 채점 모델 `gemini-3.6-flash`는 temperature를 무시해서 채점 결과가 매번 달라질 수 있다. 3단계 (b) 재채점 잡음을 반드시 측정한다.
- 임베딩 `gemini-embedding-2`, `gemini-embedding-2-preview`, `gemini-embedding-001` 모두 호출되고 기본 3072차원이다.

### 4.4 비용 추정 (6절 호출 수 기준, 대략치)

가정: 답변 1회 입력 약 3,500 토큰(문맥 5청크와 프롬프트) / 출력 약 800 토큰(thinking 포함). 채점 1회 입력 약 2,000 / 출력 약 300. 답변 호출 약 1,300회, 채점 약 1,000회.

| 항목 | 토큰 | 비용 (USD) |
|---|---|---|
| 답변, 전부 `gemini-3.5-flash-lite`일 때 (기준 설정) | 입력 4.6M, 출력 1.0M | 약 3.9 |
| 답변, 전부 `gemini-3.8-flash`일 때 | 같음 | 약 7.3 |
| 답변, 전부 `gemini-3.1-flash-lite`일 때 | 같음 | 약 2.7 |
| 채점, `gemini-3.6-flash` (thinking 약 400 토큰/회 포함) | 입력 2.0M, 출력 0.7M | 약 4.1 |
| 인덱스 구축, 청킹·임베딩 변형 6번 | 약 3M | 1 미만 |
| **일회성** 페이지 추출 VLM 보충 (실측, 2026-10-20) | 입력 0.75M, 출력 0.10M | **0.92** |

비용은 두 종류로 나눠 보고한다.
- **일회성 비용**: 모든 실험이 공유하는 준비 단계. 페이지 추출 VLM 보충(실측 0.92 USD, `corpus/extraction.json`)과 인덱스 구축(설정마다 `out/index/<key>/build.json`, `summary.json`의 `index_build_usd`). 실험별 문항당 비용에는 넣지 않는다.
- **실행 비용**: 문항마다 드는 답변·검색 비용(`summary.json`의 `cost.usd`, `usd_per_question`)과 채점 비용(`judge_usd`). 설정 비교는 이 값으로 한다.

프로젝트 전체 예상은 약 10 USD 안팎이다(일회성 비용 포함)(답변 대부분이 기준 `gemini-3.5-flash-lite`, 일부가 007의 `gemini-3.8-flash`). 답변을 전부 `gemini-3.8-flash`로 해도 약 13 USD다. 실제 비용은 실행 기록의 토큰으로 계산해 PROCESS.md 장부에 함께 적는다. 2027-01-01 이후에 실행하면 flash 등급 단가가 2배가 되므로 확인일을 다시 갱신한다.

## 5. 평가 지표와 측정 방법

| 구분 | 지표 | 측정 | LLM |
|---|---|---|---|
| 검색 | page_hit@k, MRR, evid@k (근거 구절이 검색 결과에 있는 비율), gold@k (상위 k개 중 정답 페이지 청크 수) | `evalkit/metrics.py` | 없음 |
| 문맥 | 답변 단계에 넘긴 문맥의 정답 페이지 포함 여부, 근거 구절 포함률, 문맥 길이 | `metrics.context_metrics` | 없음 |
| 답변 품질 | 정답 점수 0/1/2와 채점 이유. 기준 답안, `must_include`, `must_not_include`, 근거 구절을 채점 모델에 준다 | 채점 프롬프트(1단계에서 고정) | 채점 1회/문항 |
| 근거 준수 | 인용한 (파일, 페이지)가 정답 페이지 또는 실제 넘긴 문맥 안에 있는가 | 코드로 대조 | 없음 |
| negative 대응 | 기대 행동 그룹 일치 여부. `expected_behavior` 22종을 5개 그룹으로 묶는다: 보류·자료 요청(`abstained`) / 되묻기(`clarify`) / 정정 후 답변(`answered` + 정정) / 거절(`refused`) / 주입 무시(주입을 따르지 않았는지 + 해당 그룹). 시스템의 `status`는 코드로 대조하고, 정정·주입 여부는 채점 모델이 판단한다 | 코드 + 채점 | 채점에 포함 |
| 비용 | 문항당 입력·출력 토큰(모델별), USD, 모델 호출 수, 검색 횟수, 인덱스 구축 임베딩 비용(일회성, 따로 집계) | 실행 기록에서 합산 | 없음 |
| 시간 | 문항당 응답 시간 p50/p90 | 실행 기록 | 없음 |

- 대리 지표: 4단계에서 기준 설정의 채점 결과와 가장 잘 맞는 검색 지표를 고른다. page_hit나 MRR이 맞을 거라고 미리 가정하지 않는다.
- 잡음: 같은 설정 재실행과 같은 답변 재채점으로 측정한다. 바뀐 문항 수보다 작은 차이는 결과로 해석하지 않는다.
- 실패 분류: 검색 실패 / 근거는 찾았지만 답변 불완전 / 과잉 보류 / 데이터 문제 / 평가 오류 / 모호한 질문. README가 요구하는 "검색에서 놓침"과 "근거는 찾았지만 답변 오류"는 첫 두 유형이다.

## 7. 결과 기록 항목과 저장 형식

로컬 실행 기록은 `out/runs.db`에만 두고(git 제외), 공유·제출할 결과는 `results/<experiment>/`로 내보내 git에 올린다(2026-10-20 결정). 파일 형식은 [`results/README.md`](../results/README.md)에 있다.

| 저장소 | 내용 | git | 연결 키 |
|---|---|---|---|
| `out/runs.db` (SQLite, `evalkit/runlog.py`) | 문항별 실행 전체: 질문, 답변, status, 검색 기록, 답변 단계에 넘긴 문맥, 인용, 단계별 판단, 호출 수, 검색 횟수, 토큰, 시간 | 제외 | `experiment`, `qid` |
| ↳ `config` 열 (JSON) | 모델 ID, 프롬프트 파일, 청킹·검색 설정, 검색 범위, 기준 설정 대비 변경 사항 | | `experiment` |
| ↳ `steps` 열 (JSON) | LLM·임베딩 호출마다 `{node, model, input_tokens, output_tokens, thinking_tokens, seconds}`. 모델별 USD 계산용 | | `run_id` |
| `results/<experiment>/summary.json` | 설정, 점수, 검색 지표, 비용(USD·토큰), 호출 수, 시간 p50/p90 | 모든 실험 | `experiment` |
| `results/<experiment>/grades.jsonl` | 문항별 채점: 점수, 이유, negative 행동 그룹 | 채점한 실험 | `experiment`, `qid` |
| `results/<experiment>/metrics.jsonl` | 문항별 LLM 없는 검색·문맥 지표 | 모든 실험 | `experiment`, `qid` |
| `results/<experiment>/runs.jsonl` | `runs.db`에서 내보낸 문항별 실행 기록 (`python -m evalkit.runlog export ...`) | 기준 설정, 채택한 설정, 최종 test, 007·008만 | `experiment`, `qid` |
| `prompts/*.md` | 답변·채점 프롬프트 원문. 버전마다 새 파일 | 올림 | `config`의 프롬프트 파일명 |
| `experiments/NNN-*.md` | 실험 카드: 가설, 판단 기준(결과 전에 작성), 결과, 결정 | 올림 | 카드 번호 → `experiment` |
| `submission/PROCESS.md` 7절 | 실험 요약 표, LLM 호출 장부 | 올림 | 카드 번호 |
| `submission/EVALUATION.md` | 최종 비교, 선택 이유, 실패 사례 | 올림 | – |

- 실험 이름 규칙: `<split>_<카드번호>_<변형>`, 예: `dev_000_baseline`, `dev_004_hybrid`
- 비교 방법: 같은 질문으로 문항별 짝비교(`evalkit/paired.py`, bootstrap 95% 신뢰구간). 결과는 "B 우세 N / A 우세 N / 같음 N"과 비용 변화를 함께 보고한다. 여러 실험을 나란히 볼 때는 `summary.json`을 표로 모은다.
