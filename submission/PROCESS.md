### 0. 환경과 제약

- 모델: Gemini 안정 모델만 사용(preview, 2.5 제한 접근 모델 제외). 답변 후보 `gemini-3.1-flash-lite`, `gemini-3.5-flash-lite`, `gemini-3.8-flash`(기준). 채점 `gemini-3.6-flash` 고정. 임베딩 `gemini-embedding-2`(기준), `gemini-embedding-001`(비교). ID·단가는 [PLAN.md](PLAN.md) 4절 (2026-10-20 결정)
- 마감: 2026-10-22(목). 일정과 시간이 부족할 때 줄이는 순서는 PLAN.md 9절
- 답변 실행: 001–006은 개선 여지 확인을 통과할 때만 실행한다. 007·008은 답변 단계를 바꾸는 비교라 LLM 없는 대리 지표가 없으므로 항상 실행한다 (2026-10-20 결정)
- 최종 test: T1 처음 RAG / T2 개선된 RAG / T3 Agent를 한 번씩 실행해 튜닝 효과(T2 − T1)와 구조 효과(T3 − T2)를 나눈다 (PLAN.md 3.2절, 2026-10-20 결정)
- 기본 RAG 구현: 문서 처리·Recursive 청킹·벡터 검색·BaselineRAG를 미리 구현하고 테스트했다. 답변 단계 함수(`rag.generate_answer` 등)는 Agent도 그대로 쓴다. gemini-embedding-2는 문서 권장대로 질의·문서 접두어(`task: question answering | query:`, `title: … | text:`)를 붙여 임베딩한다 (2026-10-20)
- 기본 RAG 프롬프트: Agent의 generate 노드와 같은 `prompts/answer_v1.md`를 쓴다. Agent 비교에서 구조의 효과만 보려는 것이다 (PLAN.md 3.3절, 2026-10-20 결정)
- 결과 공유: `out/runs.db`는 로컬에만 둔다. `results/<experiment>/`에 요약·채점·지표를 올리고, 주요 실험은 `runs.jsonl`도 올린다 (`results/README.md`, 2026-10-20 결정)
- LLM 호출 예산: 숫자 제한 없이 최소화하고 모든 호출을 7절 장부에 기록한다 (2026-10-20 결정)
- 채택 비용 상한: 고정하지 않는다. 비교하는 설정마다 품질과 함께 비용(USD)·토큰·p50/p90 응답 시간·호출 수·검색 횟수를 기록한다 (2026-10-20 결정)
- 분할: 제공 180문항을 세트×난이도(negative는 유형 포함)로 층화해 dev 90 / test 90으로 나눈다. 직접 만든 골든셋은 따로 두고 8단계에서만 평가한다 (2026-10-20 결정)
- 워크플로우와 다른 점: 과제가 청킹·검색·기본 RAG 대 Agent 비교를 요구한다. 청킹·검색은 LLM 없는 지표로 비교 결과를 낸다. Agent와 답변 모델 비교는 실패 분석 결과와 상관없이 답변 실행까지 한다
- 실행 환경: Python 3.13.13, pip + `requirements.txt`(수강 환경과 같은 버전으로 고정). API 키는 각자 쓴다. 공통 기반(설정 상속, 실행 기록, 비용 계산, 평가·결과 내보내기, 비교표)은 `src/rag/`와 `scripts/`에 구현하고 `tests/`로 검증했다 (2026-10-20 결정)
- 모델 호출 확인 (2026-10-20, `scratch/check_thinking.py`, 답변 후보 4개 × 3회 + 임베딩 3회): `thinking_level`(low/high)이 네 모델 모두에서 동작한다. LangChain의 `output_tokens`는 thinking 토큰을 포함하고 input + output = total이다. `gemini-3.6-flash`와 `gemini-3.5-flash-lite`는 temperature를 무시한다. 같은 `low`라도 3.8-flash·3.5-lite는 thinking 0, 3.6-flash는 391, 3.1-lite는 159 토큰. Gemini 3 응답 본문은 `message.text`로 읽는다. 결과 표는 PLAN.md 4.3절
- 외부 부수효과 점검: LangSmith 추적은 `.env.example`, `.claude/settings.json`, `rag.env.setup()` 세 곳에서 끈다

#### 1.1 진단

#### 1.2 처리 방식

#### 1.3 문제와 해결
_발견한 추출 문제(이미지에만 있는 정보, 깨진 표 등)와 처리 결과_

**사전 점검 (2026-10-20, 기본 RAG 구현 확인용, 실험 아님)**

- 추출: 23개 PDF, 490쪽, 모두 텍스트 레이어 있음. 범위 A 16개 파일 142쪽은 글자가 적은 쪽이 없다. 글자 80자 미만 쪽은 범위 B에만 있다: 주택연금 15쪽(이미지 243개), 정책서민금융 13쪽, 금융생활 가이드 3쪽(1·13·20), 보험약관 9쪽, 퇴직연금 27쪽. 표·그림만 있는 쪽인지 1단계 담당이 원문과 대조한다
- 버그 2건을 발견해 고쳤다: (1) `gemini-embedding-2`는 문자열 목록을 벡터 1개로 합친다 → Content 목록으로 보내고 개수를 검사한다(테스트 추가). (2) `gemini-embedding-2`는 `task_type` 대신 텍스트 접두어가 권장 사용법이다 → `embedding.text_format: gemini2_qa`
- 범위 A 인덱스(387청크, 18만 토큰, 0.036 USD)와 3문항으로 확인: 접두어 적용 전에는 POS020이 보류, 적용 후에는 근거(01_매매거래계좌설정약관 p.5)와 함께 답했다. POS001은 둘 다 보류: 정답 청크(용어집 p.1, 753자에 용어 약 8개)가 8위였다. 고정 길이 청크에 여러 용어가 섞이는 문제로, 카드 002(구조 단위 청킹)의 가설 H1과 맞는다
- 이 점검은 dev/test 분할 전에 POS001, POS020, NEG001을 봤다. 세 문항이 test에 들어가면 결과 해석 때 이 사실을 적는다
